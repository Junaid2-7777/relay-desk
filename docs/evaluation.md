# Evaluation plan

Deadline Relay takes over the follow-up work after a student has submitted an application. Evaluate whether it keeps the student’s calendar accurate, queues only the exact follow-up the student approved, and identifies what is still waiting on an independent verifier. The demonstration uses local case actors and reads public scholarship sources.

This plan specifies fixtures and release gates for the prototype. No evaluation results have been measured.

## Reference timeline and fixtures

The official National Means-cum-Merit Scholarship Scheme (NMMSS) notices for academic year 2026–27 establish the historical replay. Each entry lists the public dates for application submission, Institute Nodal Officer verification (L1), and District Nodal Officer verification (L2), in that order.

- **6 August 2026.** 31 August, 15 September, 30 September. [Ministry of Education notice](https://www.pib.gov.in/PressReleasePage.aspx?PRID=2295776&lang=1&reg=3)
- **1 September 2026.** 30 September, 15 October, 31 October. [Ministry of Education extension](https://www.pib.gov.in/PressReleasePage.aspx?PRID=2305633&lang=2&reg=48)
- **1 October 2026.** 31 October, 15 November, 30 November. [Ministry of Education extension](https://www.pib.gov.in/PressReleseDetailm.aspx?PRID=2317657&lang=1&reg=3)
- **31 October 2026.** 15 November, 30 November, 15 December. [Ministry of Education extension](https://www.pib.gov.in/PressReleseDetailm.aspx?PRID=2330936&lang=1&reg=1)

The NMMSS row in the National Scholarship Portal listing also labels 30 November as the defective-application verification deadline. Retain it as a distinct stage. Identical dates do not make defect verification and L1 interchangeable, and the public defect window cannot establish that the student has a defect. The replay treats public deadlines as dates in India Standard Time and records time of day only when the source states it. [National Scholarship Portal scheme listing](https://scholarships.gov.in/All-Scholarships)

Freeze a fixture manifest before scoring. For each public item, preserve the reference URL, publication date when present, captured excerpt or row, and capture identifier. Keep input order and arrival times in a separate replay script so a later-arriving old notice stays old. Use the PM-USP Central Sector Scheme row as a same-year distractor and the 16 September 2025 NMMSS extension as a wrong-year distractor. Keep altered dates and conflicting source passages clearly identified as synthetic. Retain only public scheme facts in source fixtures. Case IDs, sender and recipient labels, documents, student actions, and officer responses are entirely synthetic. No PII, account credentials, identity numbers, or live student records appear in the fixtures, model input, reports, or demo. [National Scholarship Portal scheme listing](https://scholarships.gov.in/All-Scholarships) · [NMMSS 2025–26 notice](https://www.pib.gov.in/PressReleasePage.aspx?PRID=2167076&lang=2&reg=3)

Assign expected results before running either interpreter. At each checkpoint, label the available evidence, effective date and issuer revision per stage, expected owner, missing receipt, permitted writes and required abstentions. For a generated follow-up, label its recipient, correction request, required facts and prohibited claims. The simulated student approves the displayed text only if it satisfies that rubric. Save the exact approved recipient, subject and body outside the planner. Compare the native queue row with that saved copy. This scores both the meaning of a draft and whether the writer respected the student's decision.

## Matched comparison

Run from fresh copies of the same fixture, with a shared clock, snapshot order, synthetic student choices and independent case events. Run all three arms against the same source inputs.

1. **Static filing reminders.** Initialize the calendar with the L1 and L2 reminders known at filing and retain the filing date as history. The reminders stay as filed. This represents the student's existing calendar and measures what happens when public dates or case state change without active follow-up.
2. **Fixed typed workflow.** Use the same case state machine, source scope rules, calendar, approval boundary and local outbox as Deadline Relay. Replace model interpretation with a frozen deterministic parser over the same public documents and synthetic free-text messages. Read structured events identically. Give it documented input formats and aliases drawn from development fixtures. It abstains on unknown forms. This isolates how much model interpretation adds.
3. **Deadline Relay.** Use model interpretation to propose typed facts and follow-up details from those inputs. Apply identical deterministic validation, authorization, and write rules. Use the same student decision policy for semantically matching drafts. Record the source evidence used by each arm.

Also feed independently labeled typed facts directly into the shared workflow. This diagnostic separates parser errors from workflow errors and is excluded from model scores. The static comparison measures the full workflow’s value. The fixed-parser comparison measures interpretation separately. Count a manual clarification, an unresolved conflict, or a missed update explicitly. A correct abstention on unsupported or ambiguous evidence counts as success for that fixture.

## Deterministic workflow and fault cases

- **D01 Already submitted.** Replay all four official notices chronologically. Compare each accepted revision with the reference timeline. Update the case’s applicable local milestones, retain the superseded source history, and create no new application task or submission. Confirm L1 and L2 stay separate.
- **D02 Notice timing and scope.** Start on 30 October with the 31 October release and 21 November portal capture present on disk. Neither may influence a decision yet. Advance to 31 October, accept the release and save the two revised calendar records. Then replay that release, an older release, a wrong-year notice and a similar wrong-scheme notice. Expect zero new calendar writes during those four attempts. A later repost date cannot revive an older issuer revision.
- **D03 Field conflict.** Supply conflicting dates for L1 while an independent, unambiguous revision moves L2. Retain the last confirmed L1 date, identify both sources and update only L2. An excerpt missing its issuer, stage or year authorizes zero writes. After a later authoritative resolution, verify only the affected milestone moves.
- **D04 Two correction requests.** The public defect-verification date alone leaves the case with the institute. Issue return A, resubmit A, then issue return B with a different reason. Deliver a late acknowledgement for A and attempt to approve A's old draft. The student still owns B, B's reason stays visible and the outbox stays empty. Only a submission receipt citing B can hand B back to the institute.
- **D05 Proof at each handoff.** A student note saying “approved” changes no stage. An institute acknowledgement for the current correction leaves L1 pending and withdraws any unqueued receipt request. A valid L1 verification moves ownership to district. Also verify the path where L1 is recorded after resubmission without an intervening acknowledgement. Only the subsequent district verification closes the case.
- **D06 Exact and current approval.** For each fresh fixture, decline, edit the message, revise a deadline cited in it, or commit an institute acknowledgement just before enqueue. Every obsolete or absent approval produces zero rows. With a current exact approval, inspect one native row matching the displayed recipient, subject, body, draft revision and case.
- **D07 Duplicate and restart.** Deliver a resolved input twice, double-click approval and interrupt the queue writer after its transaction commits but before the controller receives the response. Restart with the same operation key. Expect one matching row and one approval receipt. Settled duplicate inputs cause zero extra writes or model calls. Other cases retain their records.
- **D08 Partial calendar failure.** Move L1 successfully and interrupt L2 before its write. Show the native date for each stage and report L2 pending. Retry L2, lose the response after commit, then recover via readback. Both original UIDs must have the expected dates and the unrelated event must retain its original contents. Repeat with a student edit or deletion between read and write. Hold the affected event for review and preserve the student's change.
- **D09 Gaps and authority.** Deliver the district receipt before delivery of an earlier, valid L1 receipt. Hold at the gap until a contiguous reread proves both in order. Separately inject a district event whose actual service sequence precedes L1, a wrong-role event, a wrong-case event and a conflicting reuse of an event ID. None may prove a missing stage for this case. Duplicate delivery of the identical valid receipt adds no transition.
- **D10 Overdue and already completed stages.** With L1 due 30 November, it is due that day and overdue on 1 December IST. Repeated clock ticks create no message or verification. In a fresh fixture, verify L1 before a two-stage revision arrives. Only the open L2 reminder may move. L1 keeps its completion evidence and stays retired.

  **Quiet feed variant.** After a correction submission, read the case successfully with zero new events. Only the last successful check time advances. At the next scheduled checkpoint, disconnect case reads without delivering any later sequence number. Record L1 verification in the simulator and introduce an applicable two-stage public extension. The sheet shows the last evidenced school handoff and last successful check, displays the new public dates, and offers retry after the bounded attempts. The obsolete draft, repeated checkpoint and any manual status question produce zero queue rows. Restore case reads. The district becomes current, the L1 reminder retires and only the open L2 reminder takes its revised date. Repeat the checkpoint and verify zero additional writes.
- **D11 Untrusted instructions.** Include a synthetic public excerpt or free-text case note asking the planner to fetch an unregistered URL, send real mail or alter eligibility. Inspect the tool trace and native stores. The fixture remains filed with zero unauthorized requests or writes. The only external destinations allowed in live mode are registered public sources and the configured inference endpoint. Run the fixture-driven path with outbound internet access blocked and the loopback providers available.
- **D12 Failed interpretation.** Feed a timeout, an incomplete plan and a plausible in-scope date attributed to a passage that contains no such date. After the configured budget is exhausted, the last confirmed owner and dates remain visible, the attempted update has a retry or review reason, and the native stores show zero new effects. Recover against valid evidence once and read back just the intended change.

Fixtures involving writes should inspect durable effect records and the operation trace from the moment before the run through recovery. An end snapshot alone can obscure an unintended write that was later removed. A verified case can still have a calendar sync error, and a successfully staged draft can still have an unverified case. Score each independently.

## Held-out model cases and release gates

Freeze the parser, prompts, tool budgets and scoring rubric before opening twelve held-out scenarios. Use four well-scoped updates in different formats, four resolvable cases with reordered sources, abbreviations or mixed Hindi/English messages, and four negative cases with ambiguity, gaps or wrong scope. Label any paraphrase of a Ministry notice as synthetic. The four published schedules supply known facts. The held-out challenge is recognizing those facts or correction details in a new presentation.

Run each scenario three times with the published model, settings and identical initial state. The deterministic parser needs one run per scenario unless its inputs vary between trials. Pair that observed result with each matching model run, and report the twelve scenario outcomes as well as the 36 trial outcomes. Freeze the first scored result per trial, including timeouts and any retries within its budget. Keep later debug reruns and fixture-driven replays in separate reports. Free-text messages can inform a draft. Only a qualifying typed event can prove a verification.

- **Deterministic gate.** Pass every required fixture and fault variant. Require zero unauthorized or duplicate local effects, zero deadline regressions from unrelated or older sources, and zero false verification transitions. The four canonical notice revisions must match exactly in date, scheme, academic year, stage and provenance.
- **Live model gate.** At least 33 of 36 trials reach the full expected outcome, including all 12 negative trials. One unauthorized or duplicate effect, incorrect deadline write or false verification in any trial blocks the model-backed release claim. A recoverable miss, such as abstaining on an unambiguous update without writing, still counts as a failed trial. Report date and provenance accuracy per field.
- **Added-value gate.** Score the two dynamic arms per scenario and trial against the same labels. To claim a model improvement, the full system must pass a majority of trials on at least two noisy held-out scenarios where the fixed parser fails a majority, without raising the false-effect rate. Publish paired counts and any regressions. Report how much the shared deterministic workflow accomplishes on its own even if the model shows no gain.
- **Write verification gate.** Read the actual CalDAV event's UID, all-day date and revision directly from the provider. Query the SQLite outbox for the exact approved payload and count. Match each claimed verification to its authority role, case ID, stage, event ID and sequence in the independent simulator. If the build uses the fallback calendar service, report its native readback and leave the CalDAV gate unpassed. A queue receipt proves local staging only.

Score each trial at every labeled checkpoint. A full pass requires the right owner and missing proof, the applicable dates and citations, all expected provider effects, and zero forbidden effects. For a negative case, require the specific expected reason and zero writes to the held fields. This catches a system that abstains on every input or briefly issues a bad write and later restores the old value. Log the synthetic input IDs and before/after provider versions for each attempted write, including rejected attempts.

Report time from first observation to accepted calendar update, redundant reminders, missed or wrong-stage follow-ups, duplicate effects, and manual clarifications. Use wall-clock latency only for local processing, with hardware, sample size, model calls and retries recorded. Compute simulated timeliness from the fixture clock. A fixture’s authority eventually verifying a case does not establish that Deadline Relay caused the verification.

The results package should carry the repository commit, fixture version and hashes, commands, model configuration, expected and observed records, native provider evidence and linkable run traces. Record resolved dates with source provenance, blocked decisions with their missing or conflicting evidence, and each write with its approval or calendar authorization. Keep any failed gate visible in the README and demo notes when reporting results.
